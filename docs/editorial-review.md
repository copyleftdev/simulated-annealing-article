## Claim audit

| Draft claim or passage | Assessment | Required change or evidence |
| --- | --- | --- |
| More than 50 million configurations | Correct only with explicit integer batch sizes | Inclusive counts are 64 workers, `4096 - 32 + 1 = 4065` batch values, and `(2000 - 50) / 10 + 1 = 196` timeouts. Product: **50,991,360**. |
| More than one year at one second per evaluation | Correct for serial, continuous evaluation | **590.18 days**, about **1.62 years** using a 365-day year. State that setup, repetition, and parallelism are omitted. |
| SA sometimes accepts worse candidates | Correct | For positive temperature and finite objective values, use `delta = new - current`; accept nonpositive delta, otherwise accept with `exp(-delta / T)`. Link the original paper. |
| SA escapes local minima | Mechanism exists, success is not assured | Say it *can* escape. It must propose a path, accept the relevant moves, and have enough budget. |
| SA discovers globally better solutions | Possible, not guaranteed by this finite run | Distinguish best found from global optimum. Geometric cooling and 20,000 steps do not prove optimality. |
| Temperature means curiosity | Useful metaphor with a missing scale | Temperature has the scale of objective differences. Rescaling the score without rescaling temperature changes behavior. |
| Weighted latency, memory, throughput score | Illustrative, not a universal objective | Specify fixed normalization anchors and direction, justify weights, and impose hard service constraints separately. Do not renormalize independently for each candidate. |
| A deterministic seed reproduces a search | Conditional | Same code, inputs, RNG, and deterministic scoring can reproduce it. A real system benchmark can vary under the same seed. Do not promise bitwise agreement across unspecified platforms. |
| The supplied kernel is runnable evidence | Incomplete | It lacks a main function, actual objective, output, baseline, and tests. It is a scalar mechanism demo, not the three-parameter service experiment. |
| Firsthand years of experience | Unverified biographical statement | Remove or ask the author to replace with a true, specific example. Do not turn agent activity into a personal history. |
| Agent orchestration becomes better or cheaper | Proposed application | Show possible knobs and evaluation criteria, but claim no measured LLM quality or cost improvement from a synthetic optimizer experiment. |
| Testing ensures generalization | Too strong if implied | Held-out scenarios provide evidence for those scenarios, not a guarantee for all future production traffic. |
| Pareto frontier | Useful optional context | Define nondominance precisely: no feasible alternative improves one objective without worsening another. A weighted sum alone does not enumerate all trade-offs. |

The physical analogy, uphill acceptance, and connection to combinatorial optimization are supported by Kirkpatrick, Gelatt, and Vecchi, *Optimization by Simulated Annealing*, Science 220, 671-680 (1983). Cite the [publisher record](https://doi.org/10.1126/science.220.4598.671); the [accessible paper copy](https://cgi.cse.unsw.edu.au/~cs4601/refs/papers/KirkpatrickGelattVecchi83.pdf) supplies the original discussion. The paper does not establish that this project's chosen workload or cooling schedule beats alternative search methods.

The supplied [Cornell overview](https://optimization.cbe.cornell.edu/index.php?title=Simulated_annealing) is a secondary teaching resource. It has caveats: its stated continuity assumption does not describe the general combinatorial setting, and its pseudocode returns the current state despite prose describing the best encountered state. Use the original paper for technical authority. Do not copy those inconsistencies into the article.

## Executable evidence needed

1. Specify the search space, objective, constraints, initial state, proposal distribution, cooling schedule, stop budget, and all seeds before interpreting the results.
2. Count objective calls consistently, including the initial evaluation. Report duplicated or invalid proposals and how they consume budget.
3. Compare SA against random search and a clearly specified coarse grid under equal objective-call budgets. A prefix of a lexicographic exhaustive enumeration is not a useful grid baseline.
4. Include greedy local search using the same neighborhood to isolate the effect of accepting worse moves. Account for restarts if provided.
5. Report multiple runs of stochastic methods, including medians and spread. Do not select the nicest seed or treat one deterministic grid result as independent stochastic replications.
6. Keep oracle or exhaustive verification costs separate from search costs. An oracle for a small synthetic domain can establish regret on that domain; it does not make a huge service space tractable.
7. Report wall time with its measurement context, and distinguish optimizer overhead from objective-evaluation cost. Prefer objective-call counts for the portable headline comparison.
8. Reserve workload scenarios for final evaluation. Do not select the winning seed or retune the objective after looking at held-out results.
9. Label synthetic metrics as synthetic in the introduction, results, chart captions, and conclusion where relevant. A hand-crafted landscape is a mechanism demonstration, not a measured infrastructure saving.
10. Test bounds, invalid input, equal-score handling, RNG seed behavior, budget accounting, current versus best state, deterministic replay, and acceptance behavior. Preserve raw output and commands.

These are review criteria for this experiment, not DEV platform requirements.

## Recommended article structure

Preserve the requested title: **Stop Guessing. Let the Algorithm Find the Sweet Spot.** A precise subtitle can explain that the article contains a reproducible Rust experiment with simulated annealing, random search, and grid search.

1. Open with the familiar tuning ritual, then promise the executable comparison in the first few paragraphs.
2. Explain the valley metaphor with one labeled illustration and the distinction between current state and best observed state.
3. Introduce the acceptance formula, one numerical probability example, and the significance of temperature scale.
4. Define the concrete experiment before presenting the Rust loop. Give a command readers can run immediately.
5. Present generated results with evaluation counts and variability. Include results that do not favor annealing.
6. Explain what the experiment proves, what it leaves untested, and how to adapt the harness to actual workloads.
7. Use one compact applications table for service tuning, AI routing, test selection, and infrastructure placement. For each, identify knobs, objective, and constraints. Avoid four speculative mini-essays.
8. Close on the evaluator's role, retaining the signature sentence: **The optimizer proposes. The testing harness disposes.** Include authorship disclosure and sources.

Shorten repeated motivational passages and one-line rhetorical fragments. Keep the personality in the opening, valley metaphor, and ending; let the middle earn the argument with working code and evidence. Retain a reader question only if it invites a specific technical response.

- Image alt text explains the actual takeaway, and results remain understandable without the image.
